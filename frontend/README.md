# Дашборд прогноза пассажиропотока трамваев

Веб-интерфейс диспетчера поверх существующего сервиса прогнозов (`forecast_api.py`). Приложение на React 19 +
TypeScript собирается в **один самодостаточный файл** `static/index.html`, который сервис отдаёт по `/` без
изменений бекенда, Dockerfile и Compose. Спецификация — OpenSpec change
[`openspec/changes/build-dispatcher-dashboard`](../openspec/changes/build-dispatcher-dashboard/).

Все команды ниже выполняются из корня репозитория, если не сказано иное. Пути к Python — для Windows
(`.venv/Scripts/python.exe`); на macOS и Linux — `.venv/bin/python`.

## Требования

- Node 24 и npm (проверено: Node 24.18, npm 11.16);
- виртуальное окружение бекенда `.venv` с зависимостями `requirements-*`. Системный `python` без них даёт
  ложные ошибки тестов;
- архив датасета в `dataset/` — только для снимка разработки.

## 1. Снимок прогноза для разработки

Бекенду нужен снимок прогноза. Для разработки его строит `frontend/scripts/dev_snapshot.py`: обучает принятую
модель `pooled_route_blend` и пишет плоский снимок (`forecast.csv`, `metadata.json`, `reference_map.json`) в
папку, которая не попадает в git. Код бекенда скрипт не меняет. Снимок чужого происхождения (без метки скрипта
или с указателем `current`) он не перезаписывает.

Годовой снимок 2025-11-01…2026-10-31 в `artifacts/service` (основной для разработки):

```bash
.venv/Scripts/python.exe frontend/scripts/dev_snapshot.py
```

Двухмесячный снимок 2025-11-01…2025-12-31 — как у поставки submission. На нём проверяется, как интерфейс
обрезает горизонт «Год» и ведёт себя в режиме «Сейчас» вне покрытия:

```bash
.venv/Scripts/python.exe frontend/scripts/dev_snapshot.py --horizon submission --output-dir artifacts/service-diagnostic
```

**Если `data/processed/history.csv` не читается** (Access denied: файл создал другой агент или пользователь
песочницы), пересоберите историю в свою папку и передайте её через `--data-dir`. `data/processed` при этом не
меняется:

```bash
.venv/Scripts/python.exe -m pipeline prepare --archive dataset --output-dir <папка>/processed
```

```bash
.venv/Scripts/python.exe frontend/scripts/dev_snapshot.py --data-dir <папка>/processed
```

Флаги `--horizon` и `--output-dir` сочетаются с `--data-dir` так же, как выше.

## 2. Запуск бекенда

Bash (Git Bash, macOS, Linux):

```bash
FORECAST_DIR=artifacts/service .venv/Scripts/python.exe -m uvicorn forecast_api:app --port 8000
```

PowerShell:

```powershell
$env:FORECAST_DIR='artifacts/service'; .venv/Scripts/python.exe -m uvicorn forecast_api:app --port 8000
```

Для двухмесячного снимка укажите `FORECAST_DIR=artifacts/service-diagnostic`. Сервис читает снимок при старте,
поэтому после смены снимка его нужно перезапустить.

## 3. Фронтенд

Один раз после клонирования (из папки `frontend/`):

```bash
npm ci
```

Команды (из папки `frontend/`):

| Команда | Что делает |
|---|---|
| `npm run dev` | dev-сервер Vite на http://localhost:5173. Запросы `/health`, `/forecasts*` и `/reference-map` проксируются на бекенд `http://127.0.0.1:8000` (другой адрес — переменная `API_TARGET`). |
| `npm run dev:mock` | тот же dev-сервер без бекенда: mock-адаптер API с синтетическими данными (см. ниже). |
| `npm run typecheck` | проверка типов TypeScript (strict). |
| `npm run lint` | ESLint, предупреждения считаются ошибками. |
| `npm test` | Vitest: доменные функции, API-клиент, ошибки, mock, компоненты оболочки, скрипт проверки сборки. |
| `npm run build` | сборка одним файлом и публикация в `static/index.html` (см. ниже). |

### Mock-режим

`npm run dev:mock` запускает Vite в режиме `mock`: файл `.env.mock` задаёт `VITE_API_MOCK=1`, и клиент API
вместо сети обращается к `src/api/mock.ts`. Mock отдаёт те же формы ответов и те же ошибки, что сервис:

- годовое покрытие 2025-11-01…2026-10-31, версия `mock_synthetic:…`, режим «диагностический»;
- детерминированные почасовые значения 10 маршрутов: будни с пиками около 8 и 18 ч, выходные ровнее;
- мини-справочник остановок маршрутов 1, 5, 7, 11, 12 (несколько реальных остановок справочника, в том числе
  общие «Метро „Семёновская“» и «Улица Ибрагимова» у 11 и 12);
- ошибки 422 со строковым и списочным `detail`.

**Данные mock синтетические — это не прогноз модели.** Ссылки на CSV-выгрузки сервиса в mock-режиме не
работают: их отдаёт только настоящий бекенд.

### Сборка и поставка

`npm run build`:

1. проверяет типы (`tsc -b`);
2. собирает `frontend/dist/index.html` через `vite-plugin-singlefile`: весь JS и CSS встроены в страницу;
3. проверяет результат `scripts/verify_single_file.mjs`;
4. копирует его в `static/index.html` (`scripts/publish_static.mjs`) и проверяет ещё раз.

`verify_single_file.mjs` падает, если страница:

- ссылается на локальные файлы (`src`, `href`, `srcset`, `url()` в стилях на относительные пути) — сервис их не раздаёт;
- подключает внешние скрипты, стили или картинки. Абсолютные `http(s)` допустимы только в `<a href>`;
- больше 3,5 МБ;
- содержит маркер mock-режима `__TRAM_API_MOCK__`;
- потеряла `<html lang="ru">`, заголовок или `meta viewport`.

Проверить файл отдельно: `node scripts/verify_single_file.mjs [путь]` (по умолчанию `../static/index.html`).

После сборки перезапустите бекенд и откройте http://127.0.0.1:8000/. Страница обращается только к эндпоинтам
того же сервиса по относительным адресам.

> **Правило:** `static/index.html` — артефакт сборки. Он коммитится, но руками не редактируется и меняется
> только командой `npm run build`.

## Фильтры и показатели (раздел 2)

Чипы выбирают маршруты, «Все» включает все десять, «Снять выбор» очищает выбор. При пустом выборе
показывается «Выберите хотя бы один маршрут», запросов прогноза нет. Постоянные цвета находятся в
`src/data/route-colors.ts`; номер и галочка дублируют цвет.

Дата вводится как `ДД.ММ.ГГГГ` или выбирается в календаре. Допустимый диапазон берётся только из `/health`.
Включительные горизонты повторяют `forecast_export.horizon_end`:

- **День** — выбранная дата, детализация по часам.
- **Месяц** — начало + один месяц с ограничением числа длиной месяца, затем минус день.
  Например, 31.01.2026…27.02.2026. Детализация по дням.
- **Год** — аналогично + один год − один день, детализация по ISO-неделям.
- **Период** — две произвольные даты; до 2 дней включительно детализация по часам, до 92 — по дням,
  дальше — по неделям.

Горизонт, выходящий за покрытие, обрезается с видимой пометкой. На снимке ноября–декабря «Год» заканчивается
31.12.2025, пометка сообщает о 61 дне покрытия. Часы «с — по» включаются с обеих сторон: 7–10 означает
7, 8, 9 и 10. Детализацию и разрез «По маршрутам / Итог» можно переопределить вручную; смена горизонта или
дат снова выбирает детализацию по умолчанию. Графики и таблица подключат эти настройки в разделе 3;
общие KPI всегда суммируют выбранные маршруты.

Без фильтров в URL открываются сегодняшний день и текущий час **Europe/Moscow**, независимо от пояса
компьютера. Если сегодня вне покрытия, открывается первый день с пояснением. «Сейчас» возвращает дневной
горизонт и полный диапазон часов, сохраняя маршруты. Активный режим следует московскому часу и смене суток;
ручная дата, горизонт или час карты его выключают. Пока календарная дата не изменилась, новых запросов нет.

### Ссылка на текущий вид

Фильтры и вкладка записываются через `history.replaceState`, без перезагрузки:

```text
?routes=1,17&h=month&start=2025-11-01&end=2025-11-30&hours=7-10&g=day&split=routes&tab=map
```

Параметры: `routes` (пустая строка означает пустой выбор), `h` (`day/month/year/period`), `start`, `end`,
`hours` (`0-23`), `g` (`hour/day/week/month`), `split` (`routes/total`), `tab`
(`overview/map/table/planning/model`). При открытии сначала разбирается URL и проверяется покрытие,
затем заполняется стор и разрешаются запросы. Неверные, повторяющиеся и неизвестные параметры игнорируются
с уведомлением. Даты вне покрытия заменяются ближайшими допустимыми с указанием границ; обратный период
заменяется одним днём. Конец фиксированного горизонта вычисляется из его начала. Перезагрузка сохраняет вид;
временный режим слежения «Сейчас» в ссылку не входит.

### Данные и семантика расчётов

`useForecastSeries` использует параллельные `useQueries`: один raw-запрос на маршрут за выбранные даты.
Ключ кэша — `[forecast_version, route, start, end]`, `staleTime: Infinity`; `AbortSignal` передаётся в `fetch`.
Снятие маршрута и смена дат отменяют ненужный запрос. Часы, детализация и разрез применяются на клиенте.
У маршрутов независимые состояния загрузки, ошибки и повтор; при частичном ответе KPI помечен как неполный.
Если все запросы завершились ошибкой, нулевой итог не показывается.

`normalizeSeries` создаёт `RouteSeries { route, start, days, values: Float64Array }`, индекс
`dayIndex × 24 + hour`. Пропущенная ячейка, дубликат, чужой маршрут, дата вне диапазона или некорректное
значение — ошибка данных маршрута. Реальный ноль остаётся нулём. Ответ другой версии не попадает в кэш
текущего снимка.

Чистые функции `domain/aggregate.ts`:

- `aggregate(series, kind, hours, byRoute)` — **суммы** корзин `hour` (дата + час), `day`, `week` (ISO),
  `month`, `hourOfDay` (серверный `group_by=hour`), `weekday` (пн = 0) и `season`.
  `byRoute=false` даёт итог, `true` — отдельные строки маршрутов.
- `profile(series, 'hourOfDay' | 'weekday', hours, byRoute)` — **в среднем за день**: часовой профиль
  делится на число календарных дней, профиль дня недели — на число вхождений этого дня недели.
  Число маршрутов не входит в знаменатель. Дни недели без наблюдений не заменяются нулём.
- Сезоны: декабрь–февраль — `winter`, март–май — `spring`, июнь–август — `summer`, сентябрь–ноябрь — `autumn`.
- `calculateKpis` — сумма посадок, пик суммарного ряда с датой/часом, маршрут с максимальной суммой и
  среднее за временной час (итог / число выбранных часов за все дни, без деления на число маршрутов).
  При равных пиках выбирается самый ранний час, при равных маршрутах — меньший номер.

Расчёты сохраняют дробные значения. Только отображение округляет числа до целых в `ru-RU`.
Все календарные операции используют UTC-геттеры и ISO-строки; «сейчас» — `Intl.DateTimeFormat` с
`timeZone: 'Europe/Moscow'`.

### Проверки раздела 2

В `vite.config.ts` до загрузки тестов задан `process.env.TZ = 'Asia/Novosibirsk'`. Тесты времени используют
`vi.setSystemTime`, включая 01:30 UTC+7 → предыдущая дата, 21:00 по Москве, полночь и високосный год.
Компонентные тесты проверяют KPI, URL, пустой выбор, локальный пересчёт и независимые ошибки маршрутов;
тесты с подменой `fetch` — параллельность, кэш, отмену и смену версии.

`src/test/fixtures/forecast-real.json` снят с настоящего бекенда: `pooled_route_blend:1ad02854ca82`,
маршруты 1 и 17, 01–07.11.2025, raw и ответы `group_by=weekday/day/week`. Тест сверяет каждую корзину
с допуском ±0,5. Для повторного снятия на запущенном бекенде D3, из `frontend/`:

```bash
node scripts/capture_forecast_fixture.mjs
```

`API_TARGET` позволяет указать другой локальный адрес. Скрипт проверяет единую версию всех ответов перед
записью. Фикстура используется только тестами и не включается в production-сборку.

## Графики, таблица и выгрузка (раздел 3)

Во вкладке «Обзор» под KPI три графика ECharts. Все они берут одни и те же почасовые ряды и
агрегаты `domain/aggregate.ts`, поэтому согласованы с KPI и таблицей:

- **Динамика посадок** — корзины текущей детализации: линии по маршрутам или одна линия с заливкой
  в разрезе «Итог». Ряд длиннее 60 точек получает `dataZoom` (ползунок и колесо). Полосы отмечают
  праздники и перенесённые выходные, подсказка называет их и показывает значения в формате ru-RU.
- **Час суток** — линии среднего за день по каждому часу выбранного диапазона.
- **День недели × час** — тепловая карта среднего за день, понедельник сверху; шкала viridis
  (`LOAD_SCALE` в `src/data/route-colors.ts`) различима при нарушении цветовосприятия и в обеих темах.

Обёртка `components/charts/EChart.tsx` создаёт и освобождает график в одном эффекте, поэтому двойной
монтаж StrictMode не оставляет второй экземпляр; размер отслеживает `ResizeObserver`, опция заменяется
целиком (`notMerge`). ECharts подключён модульно (`components/charts/echarts.ts`): серии line, bar,
heatmap и компоненты grid, tooltip, legend, dataZoom, markArea, visualMap с `CanvasRenderer`.

`src/data/calendar.ts` — копия `calendar_2025.json` и `calendar_2026.json` из корня репозитория вместе
с источниками; тест сверяет копию с этими файлами. Названия праздников — по статье 112 ТК РФ
(1–6 и 8 января — «Новогодние каникулы», 7 января — «Рождество Христово» и так далее), перенесённые
выходные — «Перенесённый выходной».

Вкладка «Таблица» показывает строки текущей детализации (по маршрутам или итогом) с колонками
«База / Коэффициент / Прогноз», по 50 строк на страницу и с итоговой строкой по всему виду, а не по
странице. Коэффициент — отношение сценарной суммы корзины к базовой, взвешенное по числу посадок.

Кнопка «Скачать CSV» собирает файл текущего вида в браузере: UTF-8 с BOM, разделитель `;`, точка в
дробной части, прогнозы с тремя знаками после точки, коэффициент с четырьмя. Колонки периода
повторяют серверный CSV (`date;hour`, `date`, `week`, `month`), дальше — `route` в разрезе по
маршрутам, `base_prediction`, `coefficient`, `prediction`. Имя файла —
`tram-forecast_<горизонт>_<начало>_<конец>.csv`. Рядом ссылка на полный прогноз сервиса
`/forecasts.csv`: он за период submission, без фильтров, часов и коэффициентов.

## Сценарные коэффициенты (раздел 4)

Блок «Сценарий» задаёт ровно три поправки и не хранит их между перезагрузками:

- погода действует на все маршруты, даты и часы; пресеты взяты по измерениям там, где они есть
  («Погодные пресеты» ниже): «Ясно» 1,00, «Дождь (более 0,2 мм/ч)» 0,93, «Снегопад» 0,92,
  «Сильный мороз (ниже −20 °C)» 0,90 и «Жара (выше +25 °C)» 0,98;
- сезонная поправка включается отдельно и действует только на даты выбранного сезона: зима — декабрь–февраль,
  весна — март–май, лето — июнь–август, осень — сентябрь–ноябрь;
- одновременно задаётся одно событие: тип, коэффициент, маршруты, включительный диапазон часов и при
  необходимости включительный диапазон дат. Пресеты события: «Матч или концерт» 1,30, «Городской
  праздник» 1,20, «Ремонт или перекрытие» 0,50.

Каждый коэффициент можно править ползунком или числом от 0 до 3 с шагом 0,01. Для часа маршрута действующие
поправки перемножаются, затем результат ограничивается диапазоном `[0; 3]`. Кнопка «Сбросить» возвращает
коэффициенты к 1. Интерфейс не выдаёт допущения за расчёт модели: на погоде и событиях она не
обучена, и под выбором погоды стоит подпись, на чём держится множитель.

`domain/scenario.ts` — единственная реализация правил. `useScenarioSeries` применяет её к почасовым
`Float64Array` до агрегации и отдаёт неизменённую базу, скорректированные значения и коэффициенты каждой
ячейки. Поэтому KPI, оба линейных графика, тепловая карта, таблица и CSV меняются сразу и без новых запросов.
На графиках база остаётся сплошной линией, активный сценарий показан пунктиром; KPI показывают сценарное
значение, базу и Δ %. CSV всегда содержит `base_prediction`, `coefficient`, `prediction`.

### Погодные пресеты

`src/data/weather-effects.json` — побайтовая копия `weather_effects.json` из ветки
`feat/model-calendar-weather`: влияние погоды измерено по архиву Open-Meteo на вневыборочных
прогнозах `pooled_route_blend` за три среза май–октябрь 2025 года (95% ДИ — 10 000 бутстреп-выборок
целых дней). Файл только читается: пересчёт живёт в той же ветке, из соседней рабочей копии
ничего не импортируется.

`src/data/weather-effects.ts` отдаёт измерение категории только при `enough_data`, а `domain/scenario.ts`
собирает из него пресеты и округляет множитель до шага полей 0,01:

| Пресет | Множитель | На чём держится |
| --- | ---: | --- |
| Ясно | 1,00 | база измерения: часы без осадков |
| Дождь (более 0,2 мм/ч) | 0,93 | измерено по данным 2025 г. (Open-Meteo), 95% ДИ 0,90–0,97 |
| Снегопад | 0,92 | экспертное допущение: зимних дней в проверочных срезах нет |
| Сильный мороз (ниже −20 °C) | 0,90 | экспертное допущение: зимних дней в проверочных срезах нет |
| Жара (выше +25 °C) | 0,98 | эффект статистически не подтверждён |

Снегопад в файле есть (0,928), но стоит на 11 часах с интервалом 0,80–1,13 и `enough_data: false`,
поэтому пресет остался экспертным; морозных часов в срезах нет вовсе. У жары интервал 0,96–1,00
накрывает 1, поэтому множитель показан с оговоркой. Если в файле пропадёт измерение, пресет сам
вернётся к прежнему экспертному значению и поменяет подпись.

## Карта нагрузки (раздел 5)

Вкладка «Карта» показывает линии выбранных маршрутов на подложке OpenStreetMap. Каждая линия окрашена в один
из 5 классов нагрузки выбранного часа, а толщина (2–10 px) растёт как √ посадок в час. Значение линии:

- на одном дне (горизонт «День» или период из одного дня) — прогноз этой даты и часа;
- на многодневном периоде — среднее за день для этого часа. Подписи легенды и заголовка об этом говорят.

Классы — квантили 20/40/60/80 % всех показанных значений «маршрут × час» выбранных маршрутов после сценария,
поэтому ночью линии уходят в нижние классы, а в утренний пик — в верхние. Легенда показывает границы
классов в посадках в час; палитра viridis та же, что у тепловой карты. Маршрут без данных (загрузка или
ошибка) рисуется тонкой серой линией. Подпись номера маршрута — HTML-маркер в цвете маршрута на участке,
где рядом нет других маршрутов; её `aria-label` содержит значение и класс, чтобы нагрузка передавалась не
только цветом.

Над картой — ползунок часа 0–23, «Проиграть» (0,8 с на час по кругу, «Пауза» останавливает) и «Сейчас»
(как кнопка в фильтрах: сегодняшний день и текущий московский час). Диапазон часов фильтра ограничивает
выбор часа и проигрывание. Смена часа и сценария меняет только paint-выражения карты
(`setPaintProperty` с `['match', ['get', 'route'], …]`): данные не перезагружаются, запросов к API нет.

### Остановки

Точки остановок — для выбранных маршрутов. Маршруты 1, 5, 7, 11, 12 берут остановки из справочника
организаторов (`/reference-map`, запрос при первом открытии карты), 17, 25, 26, 28, 50 — из OpenStreetMap.
Точки ближе 60 м (гаверсинус, одиночная связь) — одна остановка с объединённым набором маршрутов; имя — из
справочника, иначе самое частое из OSM (`domain/stops.ts`). Если справочник недоступен или пуст, остановки
всех маршрутов берутся из OSM, и вкладка об этом предупреждает.

Наведение показывает название и маршруты, клик открывает панель остановки: маршруты через неё, итог и
пиковый час, график по часам выбранного дня или среднего дня периода. Прогноза по остановкам у сервиса нет,
поэтому панель показывает **сумму прогнозов маршрутов, а не посадки на остановке** и прямо это подписывает;
`stop_id` в API не отправляется. Маршруты остановки, не выбранные в фильтре, в сумму не входят, панель их
перечисляет. При активном сценарии — база сплошной линией, сценарий пунктиром, у итога база и Δ %.

### Подложка и геометрия

Подложка одна — растровые тайлы `tile.openstreetmap.org` с атрибуцией; тёмной подложки нет. Если тайлы не
грузятся, остаётся светлый фон, а линии, остановки и подписи видны: они вшиты в страницу. Ошибки тайлов не
пишутся в консоль, остальные ошибки карты — пишутся. Без WebGL вкладка показывает сообщение, остальные
вкладки работают.

Геометрия лежит в `src/data/osm-routes.json` (ODbL 1.0, © OpenStreetMap contributors) и вшита в сборку:
по одной линии на направление, склеенной из путей relation PTv2, координаты с 5 знаками. Обновление:

```
node scripts/fetch_osm_routes.mjs
```

Скрипт без зависимостей перебирает зеркала Overpass (`maps.mail.ru`, `overpass-api.de`,
`overpass.kumi.systems`, затем новые круги с паузой), отправляет POST с User-Agent проекта и таймаутом 120 с.
Relation с геометрией и теги узлов-остановок берутся одним запросом, из одного состояния базы: зеркала
живут в разных состояниях, и теги с другого зеркала теряли имена остановок. Файл записывается только после
проверки (10 маршрутов с линиями и остановками внутри bbox Москвы), поэтому неудачный запуск его не портит.
Упрощение Дугласом — Пекером (5 м) включается, только если файл больше 400 КБ; сейчас он около 234 КБ.

### MapLibre в однофайловой сборке

MapLibre GL JS 6 состоит из трёх ES-модулей: основного, общего и воркера, который импортирует общий. В
собранной странице воркер по умолчанию ищется по адресу `/maplibre-gl-worker.mjs`, которого сервис не
отдаёт. Поэтому `components/map/maplibre.ts` вшивает все три модуля строками (`?raw`), поднимает их из
blob-URL и передаёт blob воркера в `setWorkerUrl`. Общий модуль один для страницы и воркера; статический
импорт плюс самодостаточный воркер дублировали бы его (+0,5 МБ). Код MapLibre разбирается только при первом
открытии вкладки «Карта». `verify_single_file.mjs` ищет `url()` только в стилях: в скриптах это вызовы вроде
`new URL(e, import.meta.url)`, а не ссылки на файлы.

## Выпуск и «О модели» (раздел 6)

### Выпуск и расписание

Вкладка переводит прогноз посадок в оценку выпуска. По каждому выбранному маршруту она берёт пиковый час —
на одном дне прогноз этой даты, на многодневном периоде средний день, то есть те же значения, что
показывает карта, — и считает:

```
рейсы в час = ⌈B × s / (C × f)⌉        интервал = ⌊60 / рейсы⌋ мин
```

`B` — посадки маршрута в пиковый час после сценария. Допущения редактируются, изменение сразу пересчитывает
таблицу: `C` — вместимость вагона (180 пасс.), `f` — целевое заполнение (70 %), `s` — доля посадок часа,
одновременно едущих на самом загруженном перегоне (0,35). При `B = 0` вместо рейсов показано «Нет
потребности», деления на ноль нет. Рейсы округляются вверх, интервал — вниз.

Это оценка, а не расписание, и вкладка об этом говорит: посадки в час не равны наполнению вагона, а `s`,
`C` и `f` — допущения, требующие калибровки по обследованиям пассажиропотока. Правила живут в
`domain/planning.ts`, пиковый час берётся из `routeHourLoads` — той же функции, что красит карту. Значения
допущений хранятся в сторе на время сессии: по D0 они не сохраняются между перезагрузками и не попадают
в URL.

### О модели

Вкладка собрана из `src/data/model-info.ts` — зафиксированного справочника фактов из раздела design «Факты
для вкладки „О модели“». Интерфейс ничего не пересчитывает и не добавляет: он показывает снимок из
`/health` (версия, режим, покрытие), карточку модели, WAPE-score по срезам проверки, шкалу качества,
проверенные и отклонённые идеи, область определения и адаптации, источники данных со ссылками, ограничения
и план развития.

Модель определяется как часть `forecast_version` до двоеточия. В справочнике две модели:
`pooled_route_blend` (принятая) и `hist_absolute_error_depth_8_lr_0.1_iter_300` (прежний frozen winner).
Для любой другой модели метрики не показываются вовсе — только версия и ссылка на README проекта; по той же
причине скрывается раздел с результатами опытов над моделями команды. Метрики закреплены тестами
`src/data/model-info.test.ts` и `src/components/model/ModelTab.test.tsx`: они упадут, если числа изменятся.

Исключение в справочнике одно: строка об Open-Meteo в «Источниках данных» и абзац о погоде в
«Проверено и не вошло в модель» берут множители и интервалы из `weather-effects.json`, чтобы не расходиться
с пресетами «Сценария». Там же сказано, что измерено (влияние дождя на посадки, ×0,93), где измерено
(вневыборочные срезы май–октябрь 2025) и что зимние условия не оценены.
