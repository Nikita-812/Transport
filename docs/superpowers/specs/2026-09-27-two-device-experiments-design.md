# План экспериментов на Windows и MacBook

Дата: 2026-09-27. Статус: согласованное в разговоре решение, записанное для проверки пользователем. Обучение и реализация ещё не начаты.

## Цель и границы

За восемь часов одновременной работы двух компьютеров сравнить широкий набор моделей прогноза пассажиропотока, настроить лидеров, проверить устойчивость качества и производительность выдачи результатов. CatBoost — кандидат, а не заранее выбранный победитель.

Устройства:

- Windows x86-64: RTX 5070 Ti, Ryzen 7 7700, 32 ГБ DDR5.
- MacBook: M4 Pro; объём RAM пользователь не указал. Начинать с одного обучающего процесса, увеличивать параллелизм только после измерения свободной и пиковой памяти.

Восемь часов — общее настенное время экспериментального прогона после подготовки программ и установки зависимостей на обеих машинах. Разработка, перенос данных и первоначальная установка в этот бюджет не входят. Первые 30 минут прогона предназначены для проверки готовой среды и измерения пробных обучений.

Исходный ориентир — 40–60 конфигураций суммарного первичного отбора; это не гарантия. Одна конфигурация проверяется на двух срезах отбора. Число законченных запусков определяется фактической скоростью, а резерв заключительных проверок сохраняется.

В рамках этого документа определяется эксперимент, а не реализуется код. Дашборд, внешняя погода, распределённое обучение, облачная инфраструктура и повторная обработка сырых транзакций не входят в работу.

## Существующая основа

Использовать pipeline.py, test_pipeline.py, calendar_2025.json и подготовленные history.csv/future.csv. Подготовка, сезонный baseline и групповые метрики уже реализованы. Не дублировать эти контракты в отдельном экспериментальном контуре.

- История: 72 960 строк, 10 маршрутов, январь–октябрь 2025 года.
- Прогноз: 14 640 строк, ноябрь–декабрь 2025 года.
- Единица: маршрут × дата × час; target — успешные валидации.
- Полная сетка включает нули; это правило проверенных labels, не универсальное правило для произвольных источников.
- CSV: UTF-8, разделитель `;`, московские календарные часы.
- WAPE-score существующего baseline: май–июнь 0,82669; июль–август 0,77916; сентябрь–октябрь 0,86230.

API пока отсутствует. До восьмичасового прогона необходимо подготовить минимальный сервис выдачи готового прогноза и нагрузочный сценарий; иначе этап проверки RPS считается невыполненным, а не заменяется временем вызова predict.

## Подход и распределение

Выбран широкий первичный отбор с последующей настройкой сильных семейств. Глубокий поиск только по бустингам не покрывает запрошенное разнообразие; равномерный поиск по всем семействам тратит бюджет на слабые варианты.

| Устройство | Семейство | Первичные варианты |
|---|---|---|
| MacBook | Сезонные модели | Текущий baseline; среднее/медиана за 4, 8, 12 недель; профиль с весами давности |
| MacBook | Линейные модели | Ridge с взаимодействиями календарных признаков; Poisson-регрессия |
| MacBook | Деревья | ExtraTrees и Random Forest с ограниченной глубиной |
| MacBook | HistGradientBoosting | Абсолютная ошибка и Poisson |
| MacBook | LightGBM CPU | L1 и Poisson |
| Windows | CatBoost | MAE и RMSE, несколько глубин; короткое сравнение CPU/GPU |
| Windows | XGBoost | Абсолютная и квадратичная ошибка; короткое сравнение CPU/GPU |
| Windows | MLP | Небольшая сеть на общих табличных признаках |
| Windows | Временная нейросеть | DLinear как первый компактный кандидат; N-HiTS как дополнительный при готовой совместимой реализации и свободном бюджете |
| MacBook | Ансамбли | Смеси двух лидеров и лидера с baseline по сохранённым прогнозам |

У каждой модели должен быть предварительный успешный короткий запуск. Неподдерживаемое сочетание objective/backend не заменять молча: записать причину, попробовать совместимый CPU-вариант либо пропустить конфигурацию.

Windows исполняет один GPU-job одновременно. При совместном запуске CPU- и GPU-job ограничивать суммарные CPU-потоки и проверять конкуренцию за RAM. MacBook начинает с одного CPU-job; увеличение числа процессов не должно приводить к swap или ухудшать суммарную пропускную способность.

## Данные и отсутствие утечки

На устройства передаются подготовленные таблицы, календарь и метаданные. Архивы сырых транзакций не нужны. Сверяются SHA-256 таблиц и календаря, версия схемы и Git commit.

Наборы признаков проверяются последовательно:

1. Маршрут, час, день недели, рабочий/праздничный/предпраздничный день.
2. Те же признаки плюс средние/медианы по маршруту, часу и дню недели за последние 4, 8, 12 недель.
3. Изменение недавнего уровня маршрута и отдельно буднего/выходного профиля относительно длинной истории.

Для лидеров сравнить всю историю и последние 8–16 недель. Учитывать различие между окном обучающих target и историей, доступной для расчёта признаков: обе величины явно записываются в конфигурации.

Обучающие примеры с историческими признаками строятся относительно исторических дат выпуска прогноза. Для каждой такой даты все target-derived признаки используют только предшествующие доступные наблюдения, а target лежит в последующем горизонте. Примеры, target которых выходит за внешний cutoff, в обучение не попадают. Одинаковая функция строит признаки для обучения и применения. Горизонт в днях можно передавать как признак.

Все модели прогнозируют два месяца из одной точки без обновления фактическими значениями внутри горизонта. Обычные лаги, которые потребовали бы факты будущего, запрещены. Для нейросетей используются входные окна до cutoff и прямой многодневный выход; не создавать отдельную серию из часов разных маршрутов. Масштабирование обучается только на доступной истории.

Отрицательные прогнозы обрезаются до нуля до расчёта метрик. Округление не применяется при оценке. Для полностью нулевого в доступной истории маршрута используется единое для всех моделей правило нулевого прогноза, проверяемое заново на каждом cutoff.

## Протокол качества и выбор

| Назначение | Обучение до | Проверка |
|---|---|---|
| Отбор и настройка | 2025-04-30 | Май–июнь |
| Отбор и настройка | 2025-06-30 | Июль–август |
| Заключительная проверка | 2025-08-31 | Сентябрь–октябрь |
| Финальное обучение | 2025-10-31 | Ноябрь–декабрь без известных target |

Основной рейтинг: сумма абсолютных ошибок на двух ранних срезах, делённая на сумму их target. Не усреднять WAPE отдельных маршрутов. Отдельно сохранять метрики по срезам, месяцам, маршрутам, часам, типам дней и вклад маршрутов в абсолютную ошибку. При нулевой сумме target WAPE — null, абсолютная ошибка сохраняется.

Early stopping использует только внутренний временной участок обучающей истории. Длина внутренней проверки и число доступных origin фиксируются до запуска; они не должны потреблять факты внешнего среза. После выбора числа итераций разрешено переобучение на всей истории внешнего train.

Отобрать 3–4 сильных семейства, затем 2–3 финальные конфигурации. Для стохастических финалистов выполнить три seed, начиная с общего seed 42; детерминированным baseline повторное обучение не требуется. GPU-повторы могут иметь численные различия даже при фиксированном seed.

Ансамбли настраиваются только по двум ранним срезам: заранее заданные веса 0,25/0,5/0,75 между двумя прогнозами. Предсказания должны быть получены вне обучающей выборки соответствующего среза. При повторной проверке ансамбля повторять его стохастические компоненты.

Победитель определяется по объединённому WAPE ранних срезов с диагностикой отдельных срезов и разброса seed. Простой baseline остаётся допустимым победителем. Если более сложная модель улучшает общий показатель, но ухудшает один срез либо её преимущество сопоставимо с разбросом повторов, отчёт не объявляет устойчивого превосходства: показывает компромисс и сохраняет простой вариант.

Перед открытием сентября–октября на обоих устройствах сохранить общий фиксированный список финалистов, параметры, seed, веса ансамблей и выбранного по ранним срезам кандидата. Поздние результаты не используются для дополнительной настройки. Сентябрь–октябрь уже изучался в EDA и не называется независимым holdout. Если заключительная проверка противоречит выбору, описать это в отчёте без скрытого нового цикла подбора.

## Восьмичасовой график

| Интервал | MacBook | Windows |
|---|---|---|
| 00:00–00:30 | Проверки, baseline, оценка RAM и времени | Проверки, baseline, GPU smoke tests |
| 00:30–02:00 | Широкий отбор CPU-семейств | Широкий отбор GPU-семейств |
| 02:00–04:30 | Настройка CPU-лидеров | Настройка GPU-лидеров |
| 04:30–05:30 | Общий анализ, ансамбли, признаки и окна | Эксперименты с лидерами по общему рейтингу |
| 05:30–06:30 | Повторы и заключительная проверка своих финалистов | Повторы и заключительная проверка своих финалистов |
| 06:30–07:30 | Проверка артефактов, сводный отчёт | Инференс всех финалистов, нагрузочные тесты |
| 07:30–08:00 | Финальное обучение, если победитель здесь | Финальное обучение, если победитель здесь; экспорт |

Лимит первичной конфигурации — 5 минут на два среза вместе; настройки финалиста — 15 минут. Отмечать незавершённые срезы и не включать их в полноценный рейтинг. Для дорогих кандидатов первичный короткий бюджет обучения задаётся заранее, затем может увеличиваться в фазе настройки.

Не запускать работу, которая по измеренному времени не помещается до границы этапа. Прерывать превышения времени с сохранением статуса. При нехватке времени сокращать количество дополнительных конфигураций и финалистов, а не резерв проверки и экспорта. Если даже минимальные обязательные проверки не уложились, явно отметить незавершённость.

Перед измерениями производительности на Windows остановить все обучающие процессы. Во время нагрузочных тестов MacBook может продолжать анализ; если он используется как генератор нагрузки, ресурсоёмкий анализ на нём также остановить.

## Обмен и воспроизводимость

Один общий манифест содержит распределённые между устройствами конфигурации с уникальными run_id. Отдельные каталоги результатов исключают перезапись. Намеренные CPU/GPU-сравнения и повторы отличаются backend/seed, а не считаются случайными дубликатами.

После каждого запуска сохранять параметры, набор признаков, окна, cutoff, seed, версии библиотек, Git commit, хеш данных, устройство, статус, время, RAM/VRAM и прогнозы. Ошибки, timeout и нехватку памяти сохранять как отдельные статусы, не как нулевые метрики.

Передавать метрики и прогнозы после первичного отбора и перед фиксацией финалистов; модели передавать только для финалистов. Прогнозы включают route/date/hour, cutoff, prediction и идентификатор запуска. Target для оценки берётся из проверенной общей истории.

При слиянии проверять совпадение ключей, полноту горизонтов и метаданные; пересчитывать метрики общим кодом. Скорость обучения с разных устройств показывать отдельно. Версии общих библиотек согласовать, платформенные сборки и различия записать. Загружать только собственные доверенные артефакты моделей.

## Тесты и измерения

### Корректность

- Существующие тесты подготовки данных и baseline проходят до начала экспериментов.
- Проверка числа строк, уникальности ключей, календарных границ, неотрицательности и конечности прогнозов.
- Изменение или удаление target внешнего горизонта не меняет признаки, обучение и прогноз для его cutoff.
- Внутренние нормализация, кодирование и early stopping не используют внешний validation.
- Сохранение/загрузка модели и связанной подготовки признаков сохраняют прогноз в пределах явно заданного численного допуска.
- Итоговый CSV содержит ровно 14 640 строк route;date;hour;prediction, без пропусков и отрицательных значений.
- Слияние результатов отклоняет дубликаты run_id, несовпадающие данные и неполные срезы.

### Производительность моделей

Всех финалистов измерять на Windows: CPU-инференс обязателен, GPU-инференс дополнительный. Отдельно измерить загрузку модели, первый вызов и прогретые повторы для одной строки, суток маршрута и всей сетки. Указать, входит ли построение признаков во время; сохранить как полное время, так и время predict. GPU-замеры требуют синхронизации устройства.

Сохранять размер модели, время обучения и пиковые RAM/VRAM. Тайминги с MacBook полезны для планирования поиска, но не подменяют сопоставимый финальный benchmark.

### Производительность сервиса

Основной режим: предварительно рассчитанный прогноз загружается в память API; CSV готовится один раз. Сервис не обучает модель внутри запроса. Онлайн-инференс финалиста — отдельный сравнительный режим, не смешиваемый с выдачей готовых значений.

Сценарии: один час, сутки маршрута, диапазон дат, полный CSV. Нагрузка ступенями 50, 100, 200, 400 RPS; следующая ступень только при запасе. Для каждого сценария задаются точный диапазон/размер ответа и продолжительность. Измерять фактически достигнутые RPS, p50/p95/p99, долю ошибок, CPU, RAM и объём ответа. Перегрузку и недостигнутую интенсивность явно отмечать.

В часовом резерве сначала выполнить короткие ступени для всех сценариев, затем 15-минутный устойчивый прогон выбранной рабочей нагрузки. Фиксировать расположение генератора, сеть, количество workers и режим прогрева; убедиться, что генератор сам не ограничивает RPS. Не требовать от полного CSV той же пропускной способности без учёта размера ответа.

Результаты Windows относятся к Ryzen 7700 и указанной среде. Цель проекта — сотни RPS при p95 менее 200–300 мс на 2–4 vCPU и 2–4 ГБ RAM — требует отдельной проверки в ограниченной целевой среде. Запуск на мощном компьютере не подтверждает эту цель автоматически.

## Ограничения и источники

Десять месяцев истории не содержат прошлого ноября–декабря. Ни календарь, ни перебор моделей не гарантируют перенос на зиму. Новые режимы маршрутов без доступных на cutoff данных также неизвестны. Большой поиск на двух срезах может переобучить сам выбор модели; разброс seed не заменяет новые временные периоды.

Поддержка конкретной видеокарты проверяется успешным пробным обучением выбранной версии библиотеки. Не тратить восьмичасовой бюджет на сборку фреймворков из исходников.

- CatBoost: https://catboost.ai/docs/en/concepts/python-installation — готовые Windows-пакеты с GPU-поддержкой.
- XGBoost: https://xgboost.readthedocs.io/en/latest/install.html — GPU в Windows x86-64; выбирать стабильный релиз и фиксировать его, не брать dev-версию по номеру страницы документации.
- LightGBM: https://lightgbm.readthedocs.io/en/stable/Installation-Guide.html — CUDA-реализация не поддерживает Windows; в плане используется CPU.
- PyTorch: https://pytorch.org/blog/pytorch-2-7/ — появление поддержки Blackwell; это не предписание устанавливать старый релиз, совместимую текущую сборку фиксировать после smoke test.

После проверки пользователем этого документа следующий шаг — отдельный пошаговый план реализации экспериментального контура. Этот документ не разрешает запускать обучение на удалённом компьютере или считать восемь часов уже начавшимися.
