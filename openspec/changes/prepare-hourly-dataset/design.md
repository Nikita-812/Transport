## Context

Мотивация описана в proposal.md. В репозитории пока нет приложения, Python-зависимостей или кода подготовки. Прочитаны AGENT.md, README.md, EDA_REPORT.md и README внутри Archive (1).zip. Существующих OpenSpec-спецификаций нет.

Фактически присутствуют оба архива, включая train.zip; README о его отсутствии устарел. Малые labels проверены непосредственно в архиве: 46 234 и 11 317 уникальных ключей, суммы 46 912 710 и 12 754 481. Пример submission содержит 14 640 уникальных ключей. Полные raw в рамках планирования повторно не сканировались; сведения об их календарных хвостах взяты из EDA.

## Goals / Non-Goals

**Goals:** единый контракт данных и календаря, воспроизводимая подготовка и дешёвая проверка на настоящем двухмесячном горизонте. Сначала прозрачный контрольный прогноз, затем отдельные модельные эксперименты.

**Non-Goals:** повторный raw-аудит, автоматическое исправление аномалий, модели бустинга, подбор окон, погода, API и визуализация. Календарные признаки пока готовятся для следующих моделей; baseline использует только weekday и hour, не обещая учитывать праздники уже на этом этапе.

## Decisions

### 1. Labels как источник target

Читать два малых CSV непосредственно из Archive (1).zip через стандартный zipfile. Альтернатива — распаковывать и агрегировать свыше 10 ГБ raw — не нужна: организаторы разрешают обучение на labels, а EDA описывает сверку. train.zip не является обязательным входом команды подготовки. Не удалять аномалии и не восстанавливать предполагаемый спрос: цель — наблюдаемые успешные валидации.

Загрузить labels, проверить вход, затем достроить декартову сетку. Отсутствующая комбинация становится нулём согласно формату этих labels; повреждённое поле target — ошибка. Не распространять это правило автоматически на любые будущие выгрузки. Для текущего набора проверить суммарные 59 667 191 посадку. Если позднее понадобится raw-агрегация, объединять источники и фильтровать tran_date_time по календарным границам: нельзя учить на ноябрьском хвосте test.csv.

### 2. Один минимальный Python-модуль и стандартная библиотека

Предлагаемый интерфейс: `python -m pipeline prepare --archive 'Archive (1).zip' --output-dir data/processed` и `python -m pipeline evaluate --data-dir data/processed --output-dir artifacts/baseline`. В одном pipeline.py разместить общую подготовку календаря, валидацию и baseline; отдельный небольшой test_pipeline.py проверяет контракты. При ~73 тыс. строк достаточно csv, datetime, collections, statistics, zipfile, hashlib, json и argparse. Новые сторонние зависимости и отдельный framework pipeline не требуются. Версию Python фиксировать в метаданных; случайности нет, seed не нужен до появления стохастической модели.

### 3. Явные выходные файлы

- `history.csv`: route,date,hour,boardings,weekday,month,is_weekend,is_holiday,is_workday,is_preholiday.
- `future.csv`: те же поля без boardings; также без prediction или target.
- `metadata.json`: SHA-256 именно входных labels, имя архива и членов, периоды, строки, суммы, число добавленных нулей, версия схемы/Python, источник и хеш календаря.

CSV сохранять с `;`, UTF-8, датами ISO и сортировкой route,date,hour. Сначала полностью проверить входы и таблицы, затем записывать результаты; не публиковать новые таблицы при ошибке проверки. Пример submission читать только как ключи для проверки будущей сетки, значения prediction игнорировать. Производные файлы и архивы исключить из Git.

### 4. Зафиксированный календарь, без сетевого запроса при запуске

Небольшой версионируемый файл `calendar_2025.json` хранит официальные праздники, перенесённые выходные/рабочие и сокращённые предпраздничные дни, а также первичные ссылки. При реализации проверить календарь РФ на 2025 год по официальным источникам, включая переносы ноября и декабря, и зафиксировать контрольные даты в тесте. Конкретные даты здесь не считаются проверенными. Остальные дни выводятся из weekday; переопределения календаря имеют приоритет. is_weekend описывает обычный день недели и не подменяет is_workday. Использовать календарные часы из labels как местные часы Москвы; не преобразовывать их в UTC. Официальный производственный календарь — признак возможного спроса, а не доказательство режима работы маршрута.

### 5. Замороженный baseline и несколько срезов

Среднее по route × weekday × hour считать заново внутри каждого train-среза по полной сетке, включая нули. Фолбэк — route × hour, маршрут, ноль. Передавать прогнозу только ключи и календарь будущих дат. Target периода проверки присоединять только при подсчёте метрик. Не добавлять target-derived признаки в общий history.csv: это избавляет от риска заранее посчитать их на всей истории.

Срезы: январь–апрель → май–июнь; январь–июнь → июль–август; январь–август → сентябрь–октябрь. Горизонт — два календарных месяца, поэтому ранние срезы могут иметь 61 или 62 дня. Месячная схема из раздела 14 EDA полезна для другой задачи, но не заменяет этот протокол. Обновление по сентябрю для прогноза октября запрещено. После проверки тот же baseline можно пересчитать на январе–октябре для ноября–декабря; экспорт submission не входит в этот change.

Результаты: CSV прогнозов по каждому срезу и JSON метрик. Считать WAPE по суммам; для нулевого знаменателя писать null и абсолютную ошибку. Диагностика по месяцу, маршруту, часу и взаимоисключающим типам дней: праздник, рабочий непраздничный, прочий нерабочий. Для пустой группы — rows=0 и null-метрика. Метрики до округления. Число 0,869 из EDA — ориентир, не жёсткий критерий приёмки и не обещание будущего качества.

## Risks / Trade-offs

- Ноль может скрывать остановку движения или сбой регистрации → сохранять target без коррекции, показывать нулевые доли и маршрутные ошибки; не утверждать, что измерен скрытый спрос.
- EDA уже изучал сентябрь–октябрь и маршрут 50 → этот holdout не является нетронутым; не вводить ретроспективные правила для августовской точки прогноза.
- Ноябрь–декабрь отсутствуют в обучении → month не обеспечивает изученную зимнюю сезонность; фиксировать ограничение в отчёте, не раздувать признаки.
- Производственный календарь не описывает все изменения движения → не строить специальные маршрутные поправки без доступного на момент прогноза источника.
- Baseline игнорирует календарные исключения и смены режима → использовать как прозрачную точку сравнения; усложнять отдельным change после измерения ошибки.

## Migration Plan

Изменений существующих API и данных нет. Добавить модуль, календарь и минимальные проверки; выполнить подготовку и оценку, обновить README и уточнить отличие нового протокола от месячной проверки EDA. Исходные архивы не изменять. Откат — удалить производные результаты и откатить код; исходные данные остаются доступными.
