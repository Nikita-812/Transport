## Context

Мотивация — proposal.md. Исходный согласованный документ: docs/superpowers/specs/2026-09-27-two-device-experiments-design.md. В проекте есть один stdlib-модуль pipeline.py и unittest-проверки; сторонних зависимостей, API и runner нет. SLICES, ROUTES, календарь, fit_seasonal и build_metrics уже определены. read_history разбирает строки, но эксперименту дополнительно нужна проверка полной сетки и хешей. .gitignore исключает только существующие baseline-артефакты, а не будущие результаты моделей.

Основных specs пока нет. Завершённый prepare-hourly-dataset ограничивает признаки baseline календарём; это ограничение первого этапа сохраняется в его evaluate. Новые исторические признаки относятся только к новому экспериментальному контуру, поэтому изменение старых delta-specs и архивирование предыдущего change не требуются.

## Goals / Non-Goals

**Goals:** один переносимый контракт результатов, минимальный локальный runner на каждом устройстве, разделение обучения/оценки, гарантированный временной резерв, сопоставимые конечные замеры.

**Non-Goals:** брокер задач, автоматическое удалённое управление ПК, новый framework ML, сервер экспериментов, фронтенд, GPU на Mac, Docker/Linux SLA-проверка в восьмичасовом бюджете. Доступ к Windows не предполагается: запуск и обмен каталогами выполняются локальными командами на устройствах.

## Decisions

### 1. Отдельные небольшие модули поверх pipeline

Добавить experiments.py для CLI/runner/merge, features.py для origin-aware данных, models.py для табличных кандидатов и lazy imports, neural_models.py для компактных torch-моделей, forecast_api.py и benchmark.py. Конкретные функции не образуют plugin-framework: простой реестр имён и общие операции fit/predict/save/load достаточны. Не создавать по пакету на каждый алгоритм. Переиспользовать константы, календарь и метрики pipeline; существующие prepare/evaluate не требуют ML-зависимостей.

Предлагаемые CLI-команды: preflight, run --device windows|mac, merge, freeze, final-check, export в experiments; inference и http в benchmark. preflight и smoke не запускают восьмичасовую кампанию. run требует явно созданного манифеста с общим UTC start/deadline. Для локальных timeout использовать монотонные часы; при старте сверять оставшееся время по UTC и не продлевать его при resume.

### 2. JSON-манифест и файловые результаты вместо распределённой системы

configs/experiments.json задаёт эксперимент, стадии, seed, конфигурации и назначение устройств. Базовые конфигурации заранее распределены; дополнительные фазы получают явные revision манифеста после общего раннего рейтинга. Старые revision сохраняются. Изменение модели/признаков/параметров порождает новый run_id. result.json хранит revision/hash; merge проверяет его по сохранённому манифесту, а не отвергает законные ранние результаты после расширения очереди. Хеш окончательного freeze отдельный и неизменяемый.

Каталог artifacts/experiments/<experiment_id>/<device>/<run_id>/<attempt_id>/ содержит result.json, predictions.csv и при необходимости модель. result.json: идентичность входа/кода, config, status, timestamps, elapsed_seconds, resources, versions, error. Прогнозы содержат run_id, cutoff, route, date, hour, prediction. Target берётся только при оценке из проверенной истории.

Запись в соседние временные файлы с атомарной заменой; completed выставляется последним. После сбоя running становится interrupted при resume. Завершённый валидный результат не перезаписывается; новая попытка получает новый attempt_id. Идентичный импорт игнорируется, конфликтующий отклоняется. Файловый обмен предпочтительнее сетевого сервиса для двух компьютеров; передаются метрики/прогнозы и финальные модели, не raw-архивы.

### 3. Бюджет и ограниченный поиск

Границы стадий от общего старта: 30, 120, 270, 330, 390, 450, 480 минут. Смысл стадий соответствует согласованному документу. Лимит конфигурации вместе с подготовкой и двумя срезами — 5 минут на отборе, 15 минут при настройке; effective deadline — минимум лимита, границы стадии и всей кампании. Запускать jobs дочерними процессами и завершать дерево процессов при timeout; psutil даёт кроссплатформенные ресурсы/процессы. Не держать GPU-job в том же процессе, который должен его прервать.

Mac: один job по умолчанию; Windows: один GPU-job, CPU-пробы последовательно по умолчанию. Увеличение параллелизма допускается лишь после preflight и фиксируется в revision. Оценка длительности — максимум последних измеренных времён сопоставимых jobs; неизвестному кандидату резервируется полный лимит. Не помещающийся job получает skipped с причиной budget. Deadline включает ожидание ручного обмена, поэтому обе машины должны быть готовы до старта.

Первая очередь покрывает семейства до вариаций параметров. Затем использовать воспроизводимый random search по конечным небольшим диапазонам с seed 42, без полного декартова перебора и обязательного Optuna. Ориентир 40–60 стартовых конфигураций уточняется замерами, а не превращается в критерий приёмки. Отбор 3–4 семейств и 2–3 финалистов выполняется по сохранённому общему рейтингу. Резерв финальных фаз не расходуется на дополнительный поиск.

### 4. Конкретный каталог и зависимости

Mac: среднее/медиана последних 4/8/12 недель, среднее всей истории, экспоненциальные веса давности; Ridge/PoissonRegressor с календарными взаимодействиями; ExtraTrees/RandomForest; HistGradientBoosting absolute_error/poisson; LightGBM L1/poisson. Windows: CatBoost MAE/RMSE; XGBoost absolute/squared error на поддерживаемом backend; MLP; DLinear. N-HiTS — дополнительный кандидат только при готовой совместимой реализации и свободном времени, без обязательной новой зависимости.

Стартовые пространства: глубины бустингов 4/6/8, learning_rate 0,03/0,1, до 500/1000 итераций с внутренним stopping; LightGBM 15/31/63 листа; леса 100/300 деревьев и depth 8/16; регуляризация Ridge 0,1/1/10/100. Не все сочетания обязательны. Для neural ограничить ширину MLP 64/128, 1–2 слоя, до 50 эпох; DLinear — вход 4/8 недель. Все реально проверенные параметры сохраняются.

Зависимости: numpy/pandas/scikit-learn для таблиц, lightgbm на Mac, catboost/xgboost/torch на Windows, fastapi/uvicorn для API, psutil/httpx для измерений. Общий Python 3.13.5 из проекта проверяется до установки; несовместимый пакет отмечается, переход версии не выполняется скрыто. Раздельные platform lock-файлы содержат точные версии/источники сборок; общий код и общие пакеты согласованы. Чистую установку и GPU smoke выполняют до кампании, из исходников библиотеки в восьмичасовом окне не собирают. Документированные варианты Windows/Blackwell сверяются по источникам из исходного плана на момент подготовки.

### 5. Признаки и origins без будущих фактов

Для простого календарного набора достаточно исторических строк. Для наборов с профилями строить примеры (origin, route, target_date, hour): origin каждые 7 дней после минимум 28 дней истории, target на 1–62 дня вперёд в пределах внешнего cutoff. Каждый origin использует только свою прошлую историю. Недоступные 8/12-недельные окна используют имеющуюся историю с признаком числа наблюдений; не подставляют будущие значения. Для групп без наблюдений — route/hour, затем route, затем 0. При коротком окне обучающих target ограничивать target_date, а не расширять доступную историю.

Повторные target на нескольких origins — это разные задачи прогноза; чтобы даты с большим числом origins не доминировали, вес строки равен обратному числу примеров данного route/date/hour. Этот вес применяется только в origin-expanded обучении, не в оценке. Все датасеты строить порциями или переиспользовать по хешу cutoff/feature_config, не копировать десятки полных матриц в память. Кэш включает происхождение данных и не содержит validation target.

Внутренний stopping: последние 28 календарных дней внешнего train — inner validation; модель inner обучается только до предыдущего дня, прогнозирует эти 28 дней из одной точки. Подбор числа итераций использует только inner validation, затем обучение повторяется на полном внешнем train с фиксированным числом итераций. Внутренние примеры также обрезаются по inner cutoff. Если истории недостаточно, использовать заранее фиксированное число итераций с записью причины.

DLinear использует отдельные временные ряды маршрутов, без склеивания концов разных маршрутов, вход 28/56 суток и прямой выход 62×24 часа; для 61-дневного горизонта лишний день отбрасывается. В обучении нужны целиком известные выходные окна. Нормализация на train, её параметры сохраняются. Никаких recursive обновлений фактами внутри горизонта.

### 6. Отбор, фиксация и экспорт

build_metrics переиспользуется на каждом срезе; общий рейтинг — отношение сумм ошибок/target ранних срезов. У завершённых конфигураций одинаковая полная сетка. Для seed 42/43/44 сохраняются отдельные прогнозы и mean/min/max/std WAPE. Основной отбор — mean объединённого WAPE завершённых повторов; до повторов — seed 42. При равенстве до 1e-6 выбирать меньший сохранённый артефакт, затем лексикографически меньший config_id. Поздние замеры скорости не участвуют в этом выборе, поскольку выполняются после freeze. Если преимущество меньше максимального std WAPE сравниваемых стохастических кандидатов либо ухудшился один срез, отметить его как неустойчивое и сохранить baseline как запасной вариант; формального статистического доказательства трёх seed нет.

Ансамбли — взвешенные пары ранних прогнозов с весами 0,25/0,5/0,75; компонентов максимум два. freeze.json содержит финалистов, выбранную конфигурацию, seeds, веса, input/code hashes и подпись содержимого SHA-256. Хеш — контроль целостности, не криптографическая авторизация. final-check требует freeze и не изменяет выбор по сентябрю–октябрю. Механизм ограничивает workflow, но не скрывает уже доступную локальную историю от человека.

Финальное обучение выбранной конфигурации на январе–октябре с seed 42 (ансамбль — seed 42 каждого компонента), без выбора удачного seed по сентябрю–октябрю. Публиковать bundle с преобразованиями и готовую future-сетку атомарно. Сериализация — нативная библиотечная, плюс JSON метаданных; загружать только доверенные локальные артефакты. Проверка round trip и переноса на Windows: rtol 1e-5, atol 1e-6. Данные/модели исключить из Git, в отчёт включить относительные пути и хеши.

### 7. Сервис готового снимка и отдельный онлайн-режим

FastAPI загружает проверенный CSV и metadata на старте, индексирует по route/date/hour в памяти и сохраняет готовые CSV-байты. GET /forecasts, /forecasts.csv, /health следуют spec; без БД и Redis. Версия снимка — хеш CSV и идентификатор модели. Обновление только перезапуском процесса для этой версии; hot reload не нужен. Параметры валидируются до lookup; ошибка исходного снимка завершает старт, ошибка запроса возвращает 422.

Для сравнения добавить явно включаемый локальный benchmark-режим online с теми же фильтрами и результатом, модель загружается один раз на старте, inference не запускает обучение и не изменяет профиль истории. Режим выбирается параметром запуска сервиса, а не скрытым переключением в запросе; отражается в health и отчёте. По умолчанию готовый снимок. Он может быть создан baseline до окончательного выбора: HTTP-нагрузка не должна зависеть от финального обучения в последние 30 минут.

### 8. Производительность и тесты

Одинаковые запросы на Windows после остановки обучения. Inference: загрузка, первый вызов, затем 5 прогревов и 30 замеров для одной строки, 24 строк маршрута и 14 640 строк. Сохранять predict и end-to-end отдельно; GPU синхронизировать. RAM учитывать по дереву процессов; VRAM опрашивать доступным NVIDIA-инструментом, недоступность явно указывать.

HTTP default-профили: route 17, 2025-11-03 hour 8; те же сутки; route 17 за 1–7 ноября; полный CSV. Ступень: 10 секунд прогрева и 30 секунд измерения, rates 50/100/200/400. Дальнейшая ступень не выполняется при ошибках >1%, p95 >300 мс либо недостижении 95% заданного RPS. Это правило остановки benchmark, не обещание SLA. Для устойчивого прогона выбрать наибольшую прошедшую ступень запроса суток; если нет — отметить отсутствие допустимой нагрузки. 15 минут при выбранной интенсивности. Основной режим проходит весь набор, online — короткие сравнения в оставшемся резерве с явным статусом покрытия.

Генератор на httpx использует расписание поступлений, учитывает опоздания относительно планового старта, ошибки и пропущенные запросы, ограничивает число in-flight вместо неограниченного накопления. Отчёт различает offered/started/completed RPS. Предпочтительно Mac как генератор по LAN, при этом его обучение/анализ остановлены; loopback допустим с указанием конкуренции за CPU. Скрипт фиксирует сеть и источник. Не объединять сетевые измерения с другими условиями.

Минимальные unittest-проверки по контрактам: несовпадающий вход/дубликаты; отсутствие утечки с изменённым validation; ранжирование по суммам; timeout/resume с маленьким дочерним процессом; merge/freeze; round trip; API valid/invalid; отчёт генератора при недостижимом RPS. Не создавать тест на каждую комбинацию параметров. Полный двухустройственный прогон и измерения — отдельные этапы приёмки, которые нельзя объявить выполненными на одной локальной машине.

## Risks / Trade-offs

- [Много кандидатов на двух срезах переобучают выбор] → общий протокол, замороженная поздняя проверка, отчёт по срезам, без гарантии зимнего качества.
- [Большие origin-expanded таблицы и неизвестная RAM Mac] → порционная подготовка, один job по умолчанию, замер памяти, лимиты процессов.
- [Windows/GPU несовместимость] → preflight до таймера, CPU-проба как отдельная конфигурация, отсутствие сборок из исходников.
- [Обмен каталогами задерживает кампанию] → общий UTC deadline, небольшие файлы, резерв не продлевается; неполные фазы видны в отчёте.
- [Полный CPU round trip нейросети дорог] → короткий smoke до кампании, лимиты и явный статус недоступности вместо вымышленной скорости.
- [Восемь часов недостаточны для полного каталога] → отсев по времени, приоритет обязательных проверок, отчёт actual coverage.
- [Мощный desktop скрывает ограничения сервера] → точное описание измеренной среды; Linux SLA и поставка Docker вне этого change.

## Migration Plan

Сначала добавить контракты конфигураций/признаков и unit-проверки, затем кандидатов/runner/merge, затем минимальный сервис и benchmark. Зафиксировать зависимости и подготовить обе среды, провести короткую сквозную репетицию с малым каталогом. После готовности устройств запустить общую кампанию, свести результаты, сохранить финальный экспорт и сводный отчёт. README получает отдельные Windows/macOS-команды и измеренные числа только после реального запуска.

Старые prepare/evaluate и данные не мигрируют. Откат — перестать запускать новые entrypoints и вернуться к baseline; исходные архивы и результаты предыдущих запусков не изменяются. Не удалять данные при откате.

## Open Questions

- Фактическая RAM и число доступных CPU-ядер MacBook — измерить preflight; безопасный default уже задан.
- Точные драйвер, версии платформенных сборок и пропускная способность LAN — измерить до кампании и сохранить; они влияют на скорость/доступность кандидатов, но не на протокол сравнения.
